## K5: is the topology guard better than the standard connectivity checks?

**Question.** SKN's guard reports β₀ (pieces) and β₁ (holes) of the Vietoris-Rips complex. The standard
tools for swarm connectivity are the graph Laplacian (its number of zero eigenvalues counts components;
its second eigenvalue λ₂, the algebraic connectivity, Fiedler 1973) and, for disk graphs, the longest edge
of the minimum spanning tree (the graph at radius r is connected iff that edge is shorter than r). β₁ as a
coverage-hole detector is also prior work (de Silva & Ghrist 2007). So the honest question is what, if
anything, the guard adds over those, and what they add over it.

**Simplest rival, run as arms.** Union-find component count; Laplacian nullity; unweighted λ₂; weighted λ₂
with edge weight w = 1 − d/r for d < r; connectivity margin m = r − (longest MST edge of the complete
distance graph). New code goes in `skn/topology.py` as functions; the guard itself is not changed.

**Scenarios** (float64 positions, comm radius r = 30 m, edges where distance < r, strict):
- Ring: six nodes on a circle of radius 20 m at angles 0°, 60°, …, 300° (node 0 at (20, 0, 0)). Side 20 m,
  second-neighbour distance 20√3 ≈ 34.64 m > r, so only the six ring edges exist: β₀ = 1, β₁ = 1.
- **D1 (radial drift):** node 0 moves +x by 0.1 m per step, steps 0..200. Its distance to both neighbours is
  √((10 + 0.1t)² + 300); this reaches 30 at t = 144.95. So both edges vanish together at step 145.
- **D2 (sideways drift):** node 0 moves +y by 0.1 m per step, steps 0..500. Distance to node 5 is
  √(100 + (17.3205 + 0.1t)²), equal to 30 at t = 109.6 → edge 0–5 gone from step 110. Distance to node 1 is
  √(100 + (0.1t − 17.3205)²), equal to 30 at t = 456.05 → edge 0–1 gone from step 457. Node 0 never comes
  within r of nodes 2, 3, 4 (closest approach to node 2 is exactly 30, not < 30, at t = 173.2, never on an
  integer step).
- **Static:** the ring, unchanged, 500 steps.

**Derived values.** λ₂ of the 6-cycle = 2 − 2cos 60° = 1. λ₂ of the 6-path = 2 − 2cos 30° = 0.267949.
In D2, for steps 0..346 node 0's nearest neighbour is within 20 m, so the longest MST edge is a ring edge,
20 m, and m = 10; d₀₁ exceeds 20 from t > 346.41, so m < 10 from step 347. In D1, m(t) = 30 − d(t); linear
extrapolation from steps 99 and 100 predicts the crossing at ≈ 146.9.

**Predictions.**
- **K5a (equivalence, 500 random clouds; seed 0; n uniform in 3..12; points uniform in [0, 10]³; r uniform in
  [1, 8]).** In all 500: β₀ from `skn.topology.betti` = Laplacian nullity (eigenvalues < 1e-9) = union-find
  count; and m > 0 exactly when β₀ = 1. Consequence if it holds: β₀ adds nothing over the standard check.
- **K5b (D1).** β₀ first exceeds 1 at step 145. Unweighted λ₂ first changes at step 145 (no earlier warning).
  β₁ first changes at step 145. m strictly decreases over steps 0..145, m(144) > 0, m(145) ≤ 0. Weighted λ₂ is
  non-increasing (tolerance 1e-12), > 0 at step 144 and < 1e-9 at step 145. The step-100 linear extrapolation
  of m lands within ±5 of 145.
- **K5c (D2).** β₁ goes 1 → 0 at step 110. Unweighted λ₂ goes from 1 to 0.267949 (±1e-6) at step 110. β₀ first
  exceeds 1 at step 457. m = 10 (±1e-9) for steps 0..346 and m < 10 at step 347.
- **K5d (anti-vacuity, static).** Over 500 steps every signal is constant: β₀ = 1, β₁ = 1, λ₂ = 1 (±1e-9),
  m = 10 (±1e-9), weighted λ₂ constant (±1e-12).
- **K5e (sabotage, `--sabotage`).** `skn.topology.betti` is replaced by one that links pairs closer than 1.2r.
  K5a and K5b must be REFUTED; exit 1.

**What a pass would mean.** β₀ is the textbook component count under another name. The early warning
before fragmentation comes from the margin m (continuous, gives a time-to-fragment) and from λ₂ and β₁
dropping when redundancy is lost (D2), not from β₀. If K5c holds, the guard's β₁ already gives the same
warning as λ₂ in D2. Neither result is novel; the point is to say plainly which signal does which job.

## K3: close the loop through the thrusters (as an option; the default design stays Chad's decision)

**Finding carried from `RESULTS_2026-09-27.md`.** `step()` moves the pose by the commanded gradient; the
allocator's output is computed and discarded. All six HETs point +0.3 in z and are clipped to [0, 1].

**What gets built.** `PropulsionAllocator(geometry="legacy" | "paired")`. "paired" adds six HETs mirrored in z
(same six azimuths, −0.3 in z): 12 HETs + 3 CMGs. `SKNV1_SovereignNode(..., closed_loop=False,
thruster_geometry="legacy")`. With `closed_loop=True`, `step()` moves the pose by the realized command
`B @ u / mass_scale` (u from `allocate`, so an unclipped u reproduces the command exactly) instead of the
commanded gradient. **Defaults are unchanged**; which one SKN should use is not decided here.

**Derived values (mass 1).** Legacy: translation block of BBᵀ = diag(3, 3, 0.54). Command +z: every HET gets
0.3/0.54 = 0.5556, realized z = 1.0. Command −z: every HET negative, clipped to 0, realized 0. Paired:
BBᵀ = diag(6, 6, 1.08). Command −z: the +z set gets −0.2778 (clipped to 0), the −z set +0.2778, realized
(0, 0, −0.5). Command +z: realized (0, 0, +0.5). Any legacy realized z is ≥ 0, because the z row of B is
≥ 0 and HET commands are ≥ 0.

**Predictions** (node starts at the origin, rotations zero, dt 0.02, mass 1):
- **K3a (allocator).** Realized translation for commands (0,0,±1): legacy (0,0,0) and (0,0,1.0); paired
  (0,0,−0.5) and (0,0,0.5); each within 1e-6.
- **K3b (legacy cannot descend).** 50 random targets (seed 1, uniform in [−10, 10]³), closed loop, 1000 steps:
  z never decreases on any step of any run; for every target with z < −1, the final |z − z_target| ≥ the
  initial |z_target|.
- **K3c (paired can).** Target (0, 0, −5), closed loop, 1000 steps: z is non-increasing at every step; final
  distance < 1.0 m. Legacy on the same target: final distance ≥ 5.0 m.
- **K3d (paired converges; an empirical guess, not derived).** Same 50 targets, paired, closed loop, 3000
  steps: every final distance < 0.5 × its initial distance.
- **K3e (anti-vacuity: the realized path is the only difference).** With HET and CMG clipping disabled,
  closed-loop and open-loop poses after 300 steps toward (5, −3, 2) agree within 1e-4, for both geometries.
- **K3f (default unchanged).** A default node (no new arguments) stepped 300 times toward (5, −3, 2) reaches
  a pose identical (exact float32 equality) to the node at `7510e5b`.
- **K3g (sabotage).** `closed_loop` ignored (pose moves by the command): K3b must be REFUTED; exit 1.

## K6: persist the vault so dropped records stay checkable

**Finding.** `vault_path` is stored and never used; after 256 commits the dropped records cannot be checked
by anyone (K4, stated limit).

**What gets built.** With `vault_path` set, each commit appends one JSON line
`{"preimage", "prev", "hash"}` (hex) and flushes. `EvidenceVault.verify_file(path)` walks the file from the
all-zero genesis. Opening a vault on an existing file verifies it first: valid → the chain continues from its
last hash; invalid → `ValueError` (fail closed). `vault_path=None` writes nothing (unchanged).

**Predictions.**
- **K6a.** 1,000 commits with a path: the file has 1,000 lines and `verify_file` is True.
- **K6b (covers dropped records).** Editing the preimage on line 10 (long dropped from memory): `verify_file`
  False, while the in-memory `verify_chain` is still True.
- **K6c.** Deleting line 500: `verify_file` False. Swapping lines 300 and 301: False.
- **K6d (stated limit, a prediction of failure to detect).** Deleting the last line (truncating the tail):
  `verify_file` True. An unkeyed chain cannot detect tail truncation; this is registered so it is not later
  presented as a strength.
- **K6e (resume).** A second vault opened on the K6a file, 500 more commits: 1,500 lines, `verify_file` True.
  Opening a vault on the K6b-tampered file raises `ValueError`.
- **K6f (unchanged without a path).** `vault_path=None`: no file is created; all existing tests pass.
- **K6g (sabotage).** `verify_file` checks only the `prev` links, not the hashes: K6b must be REFUTED; exit 1.

**What K6 does not do.** The file is not signed; anyone who can write it can rewrite the whole chain
consistently. No fsync guarantee across power loss. Tail truncation is undetected (K6d).
