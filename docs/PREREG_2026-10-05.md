# Registered before the fix (2026-10-05): the evidence vault's 256-record window (K4)

Author of this round: Claude (Opus 5.5, Anthropic), at Chad Holland's direction (2026-10-05). Each prediction
is written before the code it tests. Review level: direction only, no line review before this commit.

## Finding (read from the code, then probed once, before this registration)

`EvidenceVault.commit` keeps only the newest 256 records (`self._records[-256:]`), but `verify_chain`
still expects the first retained record's `prev` to be the all-zero genesis hash. So an untampered vault
that has received more than 256 commits reports itself broken. Every `SKNV1_SovereignNode.step` commits
once, so a node fails its own check after about 255 steps; the live dashboard (`skn_orbital_tui.py`) shows
`verify_chain BROKEN` for an honest chain. The tests and the 30-second demo never exceed 11 records.

**Disclosed:** the defect was confirmed by one exploratory probe before this file was written:

```
10 commits -> verify_chain True  chain_length 10
256 commits -> verify_chain True  chain_length 256
257 commits -> verify_chain False  chain_length 256
300 commits -> verify_chain False  chain_length 256
```

V1 below therefore restates an observed fact; it is registered so the harness checks it, not as a test of
foresight.

## K4: anchor the retained window

When records are dropped, the vault keeps the `prev` of the oldest retained record as `anchor`, and
`verify_chain` starts from `anchor` instead of the genesis hash. Records already dropped cannot be checked
by anyone; that limit is stated, not hidden.

- **V1 (defect, unfixed code at `117f08f`).** An untampered vault with 257 commits: `verify_chain()` False.
- **V2 (fix).** Untampered vaults with 10, 256, 257 and 1,000 commits: True.
- **V3 (fix, tamper detection kept).** At 1,000 commits, each of these makes `verify_chain()` False: edit
  one retained preimage; swap two retained records; replace one retained hash.
- **V4 (anti-vacuity).** At 1,000 commits, altering the stored anchor makes `verify_chain()` False, so the
  fix is not "accept whatever the window starts with" inside the vault's own state.
- **V5 (in use).** A node stepped 300 times toward a target: `node.vault.verify_chain()` True after the fix
  (it was False before, by V1's mechanism).
- **V6 (sabotage).** Reverting `verify_chain` to start from the genesis hash makes V2 at 257 and V5 fail.

## What K4 does not do (stated before the code)

- An unkeyed hash chain can be rewritten end to end by anyone who rewrites every hash, anchor included. K4
  restores the check's honesty; it does not make the vault tamper-proof. (Same limit as before.)
- `vault_path` is stored but never written; nothing is persisted. Unchanged by K4.
- `chain_length` is the retained count, capped at 256, not the total number of commits. Unchanged; the
  README will say so.
